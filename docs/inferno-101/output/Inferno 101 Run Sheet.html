What Inferno tests

0:50
Screen

Slide 3, What Inferno tests

Say

Inferno turns requirements from a FHIR implementation guide into automated checks.

Use the AU Patient Summary kit when you have a patient summary Bundle, or a server that serves or generates one. Use the AU Core kit when you operate a FHIR server that other systems query.

These are community reference tests. They help you find implementation problems, but they do not provide certification or confer conformance status.

4

Four useful words

0:45
Screen

Slide 4, How Inferno organises a run

Say

Four words make the interface much easier to read.

A test kit covers a use case or implementation guide. A suite represents one version of that guide. A suite contains groups, usually one profile or one way of obtaining a document. Each group contains the individual tests that pass, fail, skip, omit, or error.

While fixing an implementation, run one group at a time. A whole suite is useful for a baseline, but it is slower and produces more information than you need for one change.

  • Select AU PS Bundle Instance and choose Run Tests.
  • Paste good.json into the Bundle input and run.
  • Open a passing Bundle Validation test and its Messages tab.
  • Open a Must Support test and show its populated and missing element checklist.

Say

Before I paste anything, one important rule: use synthetic data only. This is a public reference service and it is not designed to protect personal or health information.

I am choosing the AU Patient Summary suite and creating a session. The URL identifies this run. Keep it, because another person can open the same URL and see the results you are looking at.

This group accepts a Bundle directly, so no server is required. The other AU Patient Summary paths can fetch a Bundle from a server or ask a server to generate one.

I will start with an example Bundle from the implementation guide. While the validator runs, Inferno checks the Bundle, its Composition sections, referenced resources, Must Support elements, and terminology bindings.

The exact counts can change as the kit evolves, so I read the individual results rather than relying only on the total. A passing test can still contain warnings or useful information. The Messages tab tells me what the validator checked and which validator produced the message.

Must Support does not mean every element must always have a value. The checklist shows what this example populated and what it did not. Missing values may be warnings when the producer did not know the information.

A skipped test means Inferno could not run that check because a precondition was missing. I read the skip reason before deciding whether anything needs fixing.

Now I will rerun the same group with one mandatory section removed. Re-running replaces the previous result for this group inside the same session.

The validator message uses profile language, while the kit also gives a plainer description of the missing section. Both point to the same fix. Put the required section back, rerun the group, and confirm the failure has gone.

Fallback

If the live validator is slow, open the prepared clean and broken session URLs from the rehearsal checklist and continue from the Messages tabs.

Actions

  • Run the Patient group.
  • Point out SHALL, SHOULD, and MAY in test titles.
  • Open one search test and show the Requests tab.
  • Open the request URL, response status, and response body.
  • If a prepared Capability Statement failure is available, show it as an optional real-world example.

Say

AU Core tests the other direction. Inferno acts as a client and queries a FHIR server.

I am using the public AU Core test server and its synthetic patient data. When you test your own implementation, replace the endpoint and identifiers with test data from your server.

For this Patient group, Inferno runs the searches required by the guide, confirms that returned resources match the search, validates each resource against its profile, and checks Must Support coverage across the results.

The test titles preserve the guide's conformance language. A failed SHALL requirement is a clear conformance problem. A failed SHOULD or MAY result needs interpretation in the context of your implementation.

The Requests tab is the evidence trail. It shows the HTTP method, URL, response status, and body for the interaction. When a search result surprises you, start here before assuming the server or the test kit is wrong.

A wrong endpoint often causes one early failure followed by many skips. Fix the first failure, rerun the group, and then reassess the downstream results.

Fallback

If the public server is slow, use the prepared Patient group session. If the prepared Capability Statement result has changed, skip that optional example rather than explaining an outdated failure.

Reading results

1:10
Screen

Slide 5, Reading a result

Say

Here is the short version of the result states.

Pass means the assertion held. Fail means it did not hold, so open the test and read the message. Skip means the test could not run because something it needed was missing. Omit means the test did not apply. Error means something unexpected happened, such as a connection problem, malformed response, or test-kit defect.

Warnings and information messages can appear on passing tests. They are worth reading before a test event even when they do not make the test fail.
